# Безопасность выделенного сервера

[English version](DEDICATED_SECURITY.md)

Документ объясняет защиту dedicated-режима для администраторов и разработчиков
аддонов. Короткая установка находится в
[пошаговой инструкции](DEDICATED_DEPLOYMENT_RU.md).

## Главное правило

Minecraft принимает игрока только после того, как e4steam подтвердил текущего
пользователя Steam и создал короткоживущую запись допуска для того же поколения
сервера.

Если конфигурация, Steam, локальный listener или ingress guard не готовы,
сервер закрывается с ошибкой. Он не переключается незаметно на публичный TCP
или обычный offline-login Minecraft.

## Сетевая граница

- `server-ip` должен указывать на loopback: `127.0.0.1` или `::1`.
- RCON и стандартный query должны быть выключены.
- Backend e4steam принимает Steam-трафик и создаёт локальный мост только после
  авторизации.
- У прямого удалённого TCP-клиента нет записи допуска, поэтому он отклоняется.
- Посторонний локальный процесс тоже отклоняется: сам по себе loopback не даёт
  права входа.

Так обычный порт Minecraft не становится обходным путём мимо Steam-проверок.

## Порядок допуска

Для каждого соединения ядро проверяет:

1. текущий runtime и поколение сервера;
2. Steam-транспорт и подтверждённую личность;
3. версию и структуру протокола e4steam;
4. повтор, дубликат и возраст запроса;
5. лимит игроков и частоту запросов;
6. бан и защиту владельца;
7. allowlist или выбранный режим доступа;
8. обязательные addon-каналы на современном сервере;
9. Minecraft-login через авторизованный мост.

Аддон может отклонить прошедшее ядро соединение, но не может разрешить то, что
ядро уже запретило. Тайм-аут или ошибка аддона дают безопасный отказ.

## Tickets и защита от повторов

Steam auth ticket остаётся внутри ядра, имеет лимит 4096 байт и привязан к
текущему поколению runtime. Дубликаты, старые и повторно отправленные билеты
отклоняются. Буфер очищается после использования.

Addon API, команды и обычная диагностика не выдают tickets, GSLT, пароли,
cookies, API keys, join secrets, native handles и сырые handshake-пакеты.

## Идентификатор игрока

Имя, присланное Minecraft-клиентом, не используется как доказательство прав.
e4steam создаёт стабильный Minecraft UUID и безопасное имя из подтверждённой
личности Steam. Смена persona name не меняет UUID, allowlist, бан и playerdata.

Отображаемое имя остаётся персональными данными. В журналах и API нужно
использовать только минимально необходимую информацию.

## Конфиг и локальные файлы

Парсер конфига ограничивает размер и принимает только известные поля. Symlink,
небезопасный тип файла, дубликат, неизвестный ключ или попытка изменить
обязательную защиту останавливают запуск.

Runtime-хранилище доступа, ожидающие авторизации, очереди и диагностика тоже
имеют пределы. Папка сервера и резервные копии должны принадлежать служебному
пользователю. Не выдавайте право записи недоверенному пользователю панели или
моду.

## Публичный каталог

Ядро не публикует сервер в Steam Server Browser. Адрес `d-...steam` передаётся
нужным игрокам напрямую.

Addon API может передать ограниченное предложение публикации, но для реальной
публикации одновременно нужны доверенный provider, capability
`DEDICATED_PUBLICATION_PROPOSE`, разрешение в конфиге и все обычные Steam-
проверки. В core 0.3.1 provider отсутствует.

Публикация не может открыть скрытый TCP-вход или изменить порядок допуска.

## Retro-серверы

Retro Forge и Fabric используют тот же анонимный GameServer, привязку к
поколению, проверку tickets, лимит, бан, allowlist и loopback. В Java 8 пути
нет Addon API и согласования addon-каналов, но обязательные проверки ядра
сохраняются.

## Проверка администратора

- Minecraft слушает только loopback.
- Разрешён исходящий трафик Valve, но нет прямого публичного порта Minecraft.
- Config и cache принадлежат одному серверному пользователю.
- Адрес передаётся приватно; после утечки сессия заменяется.
- Аддоны проверяются как обычные серверные моды: Java-код не находится в
  песочнице.
- Перед отправкой лог читается целиком.
- При изменении сетевого протокола сервер и клиенты обновляются вместе.
- Перед изменением идентификаторов или загрузчика создаётся копия мира.

## Границы автоматических тестов

Тесты проверяют строгий конфиг, loopback-ingress, владельца ticket, жизненный
цикл, стабильный UUID и разделение клиентских/серверных классов. Аудит JAR
проверяет entrypoints и native-файлы.

Это не доказывает реальное Steam-подключение на каждой ОС. Ручные входы,
reconnect, лимит, отклонение прямого TCP и несколько клиентов записываются в
[COMPATIBILITY.md](../COMPATIBILITY.md).

Уязвимость нужно отправлять через приватную форму GitHub, а не публичный issue.
Прочитайте [SECURITY.md](../SECURITY.md) и не прикладывайте действующий адрес
или непроверенный журнал.
